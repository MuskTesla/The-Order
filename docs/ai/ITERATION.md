## 推荐目标与范围

**推荐主题：更易找到和继续玩的书架，加上可理解、可恢复的资料整理。** 不是只改首页，也不扩为全应用重写。三个相互衔接的部分构成一轮完整体验改进：

### A. 日常书架与卡片

1. 顶部集中名称、搜索、排序、网格/列表切换、添加游戏与批量选择；筛选收敛为全部/本地/愿望单、个人进度和更多条件。收藏、分类、标签、评分条件仍保留，显示可单独移除的已选条件。
2. 移除重复数字概览，不复制一套新统计；现有游玩统计能力保持可达。只在有合适候选时出现短“继续”条；当前会话的查看、结束计时仍可用。
3. 卡片保留完整封面、两行标题、进度、时长与直接动作；每卡最多一个明确标注的评分。有个人评分（包括 0）时优先个人评分，否则来源评分。未安装显示“添加本地游戏”，本地未设程序显示“设置启动程序”；正常本地不再重复标签。
4. `planned` 仅改显示为“未开始”，零安装视图为“愿望单”。不改变旧存储值、默认个人状态、评分、搜索字段、备份格式及选择范围语义。
5. 字号使用 12/13/14/16 等角色层级；本轮触及的可见中文和操作文本不靠断点缩成微字。小窗口通过换行、改列数、紧凑排列解决，不追求所有控件一行塞满。

### B. 资料整理与安装附加

1. 所有页面有常驻“资料整理”入口，角标只计需要用户决定的待核对项。轻量面板承接当前/最近任务、进度、取消、结果摘要、待核对队列以及缺资料/待设程序的直接动作。
2. 补缺项与重新识别仍是不同模式，菜单说明处理范围；全部、所选、单个和扫描范围内已入库的识别能力都保留。先完成替代入口，再移走首屏旧控件。
3. 运行状态与完成结果以任务 ID 和最新状态为准，避免导入 Toast 与进度互相矛盾；一次任务只发一次完成结果。完成横幅可以收起，队列仍能从常驻入口找回。失败、取消、未知和真实空结果分别显示。
4. 未安装条目的“添加本地游戏”先选择明确的游戏根目录，受限扫描并选择程序，将安装附加到**现有条目**，而不是普通导入后再猜测合并。保留原关联和个人名称、状态、评分、标签、笔记、记录。目录或程序选择取消，不留下空安装。
5. 根目录选择和程序候选由主进程验证，不能让页面传任意路径绕过边界。集合目录/多个候选要明确选定哪个作品目录；目录已属于其他条目、父子范围重叠，或与当前关联有已知且可核实的明确冲突时展示冲突，不静默抢占、覆盖或合并。线索不足或没有密钥是未知，不能阻止用户明确附加安装，也不隐式联网识别。用户可选择现有条目或返回普通导入，明确跨条目合并沿用已有保护。
6. 新附加目录的明确根范围用于后续去重；不回溯猜测或批量迁移旧记录的安装根目录。为已有非默认安装设置 EXE 不切换有效默认；首次安装和无有效默认时明确设置默认，安装身份变化仍推进识别代次。

### C. 可信改绑核对

1. 同时展示当前实时关联、真正用于该次识别的本地安装和候选。当前作品从书架快照读取；只有确有记录的历史来源信息才标为“识别时”，不冒充当前事实。
2. 候选可查看详细资料，区分“标题相符”与“整体身份仍有冲突/不足”；不展示排序系数为概率，不放宽章节、FD、重制、版本与独立编号冲突规则。候选详情请求隔离于个人编辑草稿。
3. “关联所选”保留明确确认；“保留当前关联”结束此次建议而不改书架；“稍后处理”保留队列；“手动搜索”复用现有搜索。未关联条目可明确“本次不关联”，不承诺自动再次检查。
4. 提交前检查条目、当前关联/安装身份及核对项是否仍是用户看到的版本；删除恢复、同 ID 新任务或影响身份和决策的名称、关联、安装编辑使旧操作失效。评分、笔记等个人字段编辑应保留并与有效提交并存，不能无故使确认失效。保留当前/确认不能移除后来生成的新建议。旧队列无新增可选字段时可打开并安全降级，不伪造本地证据。

**明确非目标：** 不新增完整整理页面、全页详情、自动保存、自动改变游玩状态、全量本地证据采集、远程浏览功能、统计/设置整体改版、云同步、自动更新；不升级依赖、不重建公开索引、不迁移个人库、不推送、发布或替换正式程序。不会为了简化入口删除已有识别范围或对个人字段的保护。

## 方案比较、收益与代价

推荐上面的 A+B+C，而非仅改名/调字：后者能缓解文案和字号，但保留过重首屏、依附横幅的核对入口，以及愿望条目安装归属问题。也不推荐立即做完整整理中心和详情重构：两者有独立信息架构与编辑语义，尚无充分运行证据，合并实施会增加交互验证面而不直接改善每日找游戏、继续玩和此次改绑决策。

- **预期收益：** 封面和启动更早进入视野；“未开始”不再和未安装混在一起；偶尔维护资料有稳定入口；用户能看清当前作品再决定改绑；稍后处理和放弃此次建议有真实、可预测的区别。
- **主要代价：** 不只是 CSS：需要重组书架、增加轻量整理面板、实现目录附加到已有条目的受限桥与事务，并增加核对项时效保护。安装附加与队列决策是主要正确性风险；视觉样式和交互入口变化是主要回归面。现有保存/识别保护应复用并补边界，不能假定“加一个可选字段”就没有成本。
- **技术依赖：** 沿用当前 Vue/KunUI、Electron IPC 和事务机制，无新运行时依赖；预计涉及 App、卡片/继续条、workspace/insights、共享类型与桥、library/main/matching 以及对应合成回归。只因实际接口变化调整相关文件，不借机模块重写。
- **依赖顺序：** 术语与可读性原则 → 书架/卡片试作 → 整理替代路径完成 → 首屏旧入口收敛；目录归属设计 → 安装附加与默认保护；核对来源/时效模型 → 当前关联显示与正确决策 → 完成提示/队列联动。三个部分都通过验收后再视为本轮完成。

## 二、整体判断

**现状**：数据与并发保护做得很细（代次、事务、待核对保留旧关联），封面卡片、纹章占位图和衬线字标有辨识度，这些值得保留。主要问题在于界面直接暴露了系统内部模型：视图、状态、安装、识别模式各自有入口，用户自己的心智模型（我有哪些游戏 → 接着玩哪部 → 偶尔整理一下）没有成为主线。具体表现为三点：

## 三、值得做的改进

### UX-01 统一游戏生命周期与术语（基础，其他项依赖它）
- **问题与证据**：`electron/library.ts:150` 的 `makeGame` 默认 `status:'planned'`，对应界面上的「想玩」。扫描导入的本地游戏因此一律显示为「想玩」（05 图：想玩 2 变为 5）。视图里的「想玩清单」指的是 `installations.length===0`（`library-workspace.ts:27`）。01 图「暮色下的风筝」同时显示「放弃」状态和「想玩清单」，按钮却是「选择启动程序」（`GameCard.vue` 中 `v-else-if="game"` 一律显示 configure）。
- **方案**：
  - 状态 `planned` 的界面文案改为「未开始」，存储值不变，备份格式零迁移。视图「想玩清单」统一改称「愿望单」，侧栏、卡片、发现页的「加入」按钮一并改。
  - 愿望单卡片的动作改为「添加本地游戏…」，选择**目录**（复用导入扫描逻辑），而不是选 exe（参见问题 P-2）。
  - 首次启动「未开始」的游戏时，计时提示里附带「标为在玩」按钮。不自动改个人状态，以符合“个人字段不被自动覆盖”的规则。
- **为什么优于现状**：统计里的「想玩 5」变得可信，「继续故事」的推荐也有意义。
- **验收**：新导入的游戏显示「未开始」；旧备份导入后显示相同；任何未安装条目都不出现「启动程序」字样；搜索「想玩」类 chip 时文案一致（全文检索「想玩清单」为 0 处）。

### UX-02 书架首屏重组：一个工具栏、一行筛选、封面优先
- **证据**：01 / 05 图的测量见上。「本地游戏」「待补资料」重复出现；收藏心形开关和侧栏「特别喜欢」重复；「本周已记录 0 秒」是无效信息（`formatPlayTime` 对 0 也输出“0 秒”）；「补全资料」「重新识别」放在状态 chip 行的右侧，和筛选控件混在一起。
- **推荐布局（1440×960，CSS px，需试作）**：
  1. 顶栏 56px：`我的书架 9` ｜ 搜索框（flex，Ctrl+K）｜ 排序 ｜ 视图切换 ｜ 主按钮「添加游戏」。
  2. 筛选行 40px：分段控件 `全部 · 本地 · 愿望单`，后面接状态 chip（未开始 / 在玩 / 已完成 / 搁置 / 放弃）和「更多筛选」（分类、标签、最低评分、仅收藏）。激活的条件显示为可单独移除的 chip，再加一个「清除」。
  3. 「继续」条 ≤ 80px：只在存在有效候选（有会话记录，或状态为在玩且可启动）时出现，内容为小封面、标题、上次游玩时间和「继续游玩」。数字卡移到「游玩统计」页。
  4. 「待补资料 / 待设启动」从标签栏移除，改为 UX-03 整理入口的计数。
- **目标**：1440×960 下第一张封面顶部 ≤ 200px，两行卡片的标题可见；1280×720 下第一行卡片完整可见（含启动按钮）。现有 `max-height:780px` 时隐藏数字卡的规则可以删除，因为数字卡已经不在首屏。
- **代码关系 / 风险**：`App.vue` 中 `smartViews`、`applyOverviewFilter`、`LibraryOverview.vue`、`library-workspace.ts` 的 `LibraryView` 都要调整。`LibraryView` 的值保留（`unmatched` / `unconfigured` 仍可由整理入口使用），偏好 `overview` 改为控制「继续」条。保留「改变筛选后清除隐藏条目的勾选」这一行为。
- **验收**：所有筛选能力仍可达；同一计数在首屏只出现一次；Ctrl+K 聚焦搜索；Esc 退出整理模式；键盘 Tab 顺序为顶栏 → 筛选行 → 卡片。

### UX-03 整理中心：识别、核对和缺项集中在一处
- **证据**：识别相关动作分布在书架（补全资料、重新识别）、选择整理（识别所选）、管理页（重新识别此游戏、刷新、关联）和导入弹窗（识别已入库游戏）。待核对只能从横幅上的「待核对 2 项」进入。06 图中 Toast 仍显示「正在自动识别封面与资料」，而横幅已是「本次资料补全已完成」，两条信息矛盾（实际观察，可能和截图时机有关）。
- **方案**：
  - 侧栏新增「整理」，角标数字为待核对数（只计需要用户决定的项）。页面分三段：①当前或最近一次识别任务（进度、取消、结果摘要）；②待核对队列（即 UX-04）；③缺资料（N）与待设启动程序（N）的列表，每行一个直接动作。
  - 书架上的两个按钮合并为一个「识别资料 ▾」：`只补缺失（N 部）` / `重新识别全部本地游戏` / `识别所选（选择模式下）`。
  - 运行中保留粘顶横幅，完成后横幅收起为 Toast 加侧栏角标。横幅可见时不再弹出内容相同的 Toast。
- **风险**：一次只能运行一个任务、不自动恢复联网、取消语义这三点不变，改的只是呈现方式。需要回归「完成 → 进入整理 → 确认 → 角标递减」以及重启后队列仍在。
- **验收**：任意页面都能在一次点击内到达待核对；任务完成后只出现一个结果提示；角标与 `metadata-matching.json` 队列长度一致。

### UX-04 核对界面：先看当前关联和本地证据，再做决定（含数据决策风险）
- **证据**：`src/shared/types.ts:58` 中 `MatchReview` 只有 `name / folderPath / reason / options`，**没有当前关联**。重新识别的提示写着“当前关联和个人记录已保留”（`metadata-matching.ts:239-240`），但用户在核对弹窗里看不到当前关联的是哪部作品，就要决定是否改绑。06 图中两个候选同名同日，只有厂商不同；第二个候选的理由写着「完整官方标题唯一对应」，而顶部说“证据接近或有冲突”，自相矛盾。候选不能打开详情；也没有「都不是」或「保持当前」的选项。
- **方案**：
  - 本地一侧显示证据卡：目录名、选定的 exe、实际读到的线索（例：`程序名称（PE）：…`、`Steam App ID：…`、`说明书标题：…`），并标注来源。
  - 重新识别类核对项增加「当前关联」卡（封面、标题、发售日、厂商），标记为“当前”。
  - 候选横向并列，**与本地线索不一致的字段高亮**。理由改为相对表述，例如“标题一致；厂商与 PE 厂商字段不符”，不展示排序系数。
  - 动作：`关联所选`（主按钮）｜`保持当前关联`（仅重新识别项）｜`都不是，手动搜索`｜`稍后再看`。「暂时跳过」改名为「稍后再看」，并说明“下次补全仍会检查”。
  - 左侧队列每项带类型标签：`新游戏` / `可能需要改绑` / `补丁或备份目录`。
  - 键盘：↑ / ↓ 切换核对项，1–3 选择候选，Enter 确认，Esc 关闭。
- **代码关系**：`MatchReview` 增加可选字段 `currentWork?`（裁剪后的作品卡片）和 `evidence?: {kind, value}[]`（有界、只含已读取的短标题与编号）。这些字段持久化在 `metadata-matching.json`，旧队列缺字段时降级显示。`preload` / `desktop-bridge` / `types` 三处需要同步。不新增任何本地读取范围。
- **验收**：对已关联的游戏制造 different-ID 的重新识别，核对页同时显示当前作品和候选；选「保持当前」后关联不变、队列项移除；旧格式队列文件能正常打开。

### UX-05 详情：作品页加就地编辑，管理区按职责拆分
- **证据**：02 图中个人状态、评分、笔记不在概览页，必须切到「管理」才能看到；标题在弹窗标题和副标题处出现两次（副标题是 originalTitle 等于 title 时的冗余）。03 图「管理」页把个人字段、安装（完整 exe 绝对路径作为主标题）、关联、识别、启动参数、移除都放在同一个滚动区。评分是自由文本框；有「保存书架信息」和「保存参数」两个保存按钮。
- **方案（保留弹窗，960px）**：
  - 概览页左栏封面下方加「个人条」：状态分段控件、评分（数字输入加步进器 0.5，有清除）、收藏、时长。笔记移到概览页正文的「我的笔记」，可折叠。
  - 标签页改为 `概览 · 角色 · 安装与资料`。安装卡片以**目录名**作主标题、exe 文件名作副标题，完整路径放进 tooltip 或复制按钮；「默认」用单选标记；启动参数按每个安装折叠显示。底部「资料关联」区显示当前作品，以及「刷新 / 重新识别 / 更换关联」。最底部的危险区放「从书架移除」。
  - 保持显式保存（以兼容现有草稿代次保护），但加「未保存」标记、Ctrl+S，关闭时如有未保存内容则确认。**不建议改成自动保存**：会改变 `detailGeneration` 草稿语义，风险高。
  - originalTitle 等于 title 时不显示副标题。
- **风险**：草稿保护逻辑（`detailGeneration`、`argumentsEditGeneration`、`syncInstallationArguments`）是关键约束，拆分时必须保留，并重跑详情 / 并发测试。
- **验收**：不切换标签就能看到并修改状态和评分；安装区在 960px 宽度下每个安装不超过 2 行；切换游戏或刷新资料时，未保存草稿的行为与现在一致。

### UX-06 封面与卡片
- **证据**：`library-layout.css` 中 `.card-image img{object-fit:contain}`，01 图 LAKE / STATION / SNOW 两侧有灰带，NIGHT 顶部有灰带。每张卡同时有封面角标的来源评分和卡内的「我的」评分。底部「本地」标签在绝大多数卡片上都一样，几乎不提供信息。
- **方案**：
  - 保留完整封面（contain），在留白处用同一张图做模糊衬底：`::before` 设为同一 URL 的背景，`filter: blur(20px) saturate(1.1)`、`transform: scale(1.15)`、`opacity: .5`。边缘因此一致，封面也不被裁切。
  - 卡片信息减到：标题（两行）→ 状态点、时长 → 启动。评分规则：有个人评分时只显示个人评分，否则显示来源评分（标注来源）；两者不同时显示。
  - 「本地」作为默认状态不再标注，只在例外时标注：`未安装`、`未设置程序`。
  - 纹章占位卡（05 图）保留，它是辨识度最好的元素之一。
- **需要试作**：模糊衬底在深色主题下的不透明度，以及 200 张卡片时的滚动性能（每张多一层合成层）。需要用真实比例（横版、方形、超长）的 CC0 夹具验证。
- **验收**：任意比例的封面在网格中外框一致；每张卡片最多一个星级；未安装和未设置程序的卡片一眼可辨。

### UX-07 字号与颜色体系（视觉一致性的前提）
- **证据（源码）**：主字号 14px，但组件实际大量使用 10–12px（order-theme.css 中 11px 有 33 处、12px 有 46 处）。断点下降到 5–9px：`brand small` 在 960px 下为 5px，`.source-badge` 7px，`.matching-heading>span` 9px（700px 下 8px），LibraryOverview 在 ≤1200px 时为 8px。在 100% 系统缩放下，这些是 8–11 个物理像素的中文。`.card-image` 在三个 CSS 文件中定义了 7 次，相互覆盖。强调色有三种：纹章深青、主按钮靛蓝、`--blue:#3995e9`。
- **方案**：
  - 字号令牌：`--fs-caption:12px`（下限）、`--fs-meta:13px`、`--fs-body:14px`、`--fs-title:16px`、`--fs-h2:20px`、`--fs-h1:26px`。规则：**断点只改布局（列数、隐藏、换行），不缩小字号**。
  - 颜色：以纹章色派生一个强调色加它的浅色版，替换 `--blue`。状态色保留语义色，不作为强调色。具体色值要试作，在明暗两种主题下都对比验证到 WCAG AA。
  - 把卡片、横幅、弹窗样式按组件归口到一个文件，删除重复规则。
- **风险**：改动面广，容易引起布局溢出。应在 UX-02 / UX-06 改版时一并做，不单独做一轮全局替换。
- **验收**：`grep "font-size:\([0-9]\|1[01]\)px"` 结果为 0；100% 与 150% 缩放下 1280×720 截图无截断；明暗主题的文字对比度 ≥ 4.5:1。

### UX-08 导入弹窗：以扫描根目录为参照
- **证据**：04 图中每行重复完整绝对路径并折成两行；「3 部可导入 / 1 部已在书架」摘要的图标错位；「识别已入库游戏」在首屏以下（README 中有提到，截图里看不到）。
- **方案**：标题下方只显示一次扫描根目录；每行显示相对路径（单行，中间省略，tooltip 显示完整路径），行高约 56px。分组为「新游戏（3）」和「已在书架（1）」，后者默认折叠，组标题旁边放「重新识别这 1 部」。发现多个程序时显示「发现 3 个程序，导入后选择」。底部固定栏：自动补全开关加主按钮「导入 3 部」。
- **验收**：1440×960 下不滚动即可看到 ≥ 5 个候选和主按钮；按钮上的数量随勾选实时变化。

### 暂不单列、需要证据后再看
- 发现页目前只能搜索（源码推断），缺少浏览入口。是否需要“按标签 / 厂商浏览远程目录”取决于 NextMoe 接口能力和配额，需要先核实。
- 游玩统计、偏好设置、深色主题没有截图，本轮不给出视觉结论。

## 四、本轮推荐

**迭代主题：“书架主路径收敛”** = UX-01 + UX-02 + UX-06 + UX-07（在书架和卡片范围内落地）+ UX-04 的最小切片（当前关联卡 + 「保持当前关联」）。

- 理由：前四项都作用于每天看到的书架，相互依赖（术语决定 chip 文案，字号令牌决定卡片尺寸），一起做才能形成完整的观感提升。UX-04 的最小切片单独纳入，因为它关系到**用户在不知道当前关联的情况下做改绑决定**的数据决策风险，后端改动小（可选字段）。
- 建议先在 `npm run dev:ui` 的预览数据上做静态原型，对比 1440×960 与 1280×720 两档，再进入桌面实现。

**暂不进入本轮**
- UX-03 整理中心：依赖 UX-04 完整版和 UX-02 的入口调整，作为下一轮。
- UX-05 详情重组：涉及草稿代次保护，风险集中，应单独一轮并配合并发回归。
- UX-08 导入弹窗：价值明确但频率低，可以和 UX-03 一起做。
- 详情改为全页、发现页浏览、统计页改版、深色主题专项：缺少证据或依赖上游能力。
