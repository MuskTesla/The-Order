## 开始使用

双击 `release\win-unpacked\The Order.exe`。请保留 `win-unpacked` 的完整目录，运行程序依赖其中的其他文件。

### 1. 配置作品数据源

打开「偏好设置」，填写并保存：

| 配置项 | 填写方式 |
| --- | --- |
| API Base URL | 默认 `https://api.nextmoe.dev/v2/` |
| API 密钥 | 在 [NextMoe 开发者平台](https://developer.nextmoe.dev/) 获取自己的密钥，需要 `catalog:read` 权限 |
| 显示成人分级作品 | 控制搜索和资料请求中的 `nsfw` 参数，保存后生效 |

点击「测试已保存的连接」。更改 API 地址的域名、协议或端口后，需要重新输入密钥；同一地址下留空则保留现有密钥。

密钥使用 Windows `safeStorage` 加密保存在本机，绑定当前 Windows 用户环境。前端只读取「是否已保存」状态，书架导出不包含密钥。换机或更换 Windows 账户后，请重新配置。

#### 程序内名称读取

「偏好设置 → 读取程序内的游戏名称」**新配置默认开启**。未包含此选项的旧设置采用新默认值；已保存的开启或关闭选择会保留。此版本仅读取游戏程序的 PE 版本资源中的作品名称、文件描述及厂商字段，有数量、读取字节和资源边界限制；不会运行程序、遍历程序代码、读取整个 EXE 或计算整个文件的哈希。

开启该选项后，识别器会读取程序的产品名称、文件描述等版本资源，不会启动游戏。**即使只是打开文件读取，Windows 安全防护也可能扫描并隔离相关文件，无需执行程序。** 可以在偏好设置中关闭此功能；关闭后继续使用目录、文件名、Steam 配置、说明书和标题索引。

检测结果需要结合文件本身判断，不能据“仅被读取”认定为误报。若怀疑误判，可通过 [Microsoft 文件分析提交入口](https://www.microsoft.com/en-us/wdsi/filesubmission) 请求复核。

### 2. 添加本地游戏

1. 点击「添加游戏」，选择单个游戏目录或存放多个游戏的文件夹。
2. 查看新游戏和已入库数量，搜索或勾选需要加入书架的游戏，再确认导入。已有目录不会重复勾选；需要重新识别时，点击「识别已入库游戏」，直接处理扫描范围内的现有记录，无需重复导入。
3. 「导入后自动补全封面和资料」默认开启。保存 API 密钥后，导入完成会开始识别；也可以关闭开关，只导入本地游戏。
4. 如果目录包含多个程序，从卡片的「选择启动程序」进入管理，指定游戏目录内的 `.exe`。同一作品的多个安装各有「设置程序」和默认启动选择。

扫描会跳过常见安装器、卸载器和运行库程序。尚未配置密钥，或已有补全任务运行时，仍可先导入本地游戏，再点击书架的「补全资料」。关联到同一作品的本地安装会合并到一个书架条目，可选择默认启动安装。

#### 补全已有游戏与核对结果

- 点击书架的「补全资料」，处理已有本地安装中尚无作品资料或缺少封面的条目。已绑定但缺少封面的游戏会按原作品编号刷新。
- 点击书架的「重新识别」，重新读取所有本地游戏的线索，包括已经有封面和资料的游戏。也可以在「选择整理」中勾选后点击「识别所选」，或从游戏的「管理 → 重新识别此游戏」只处理一部作品；未安装的想玩清单会跳过。
- 重新识别发现与现有关联不同的作品时，保留原资料并放入「待核对」，确认后才更换关联。「刷新资料」则继续更新当前已关联的作品。
- 页面顶部显示当前游戏、处理进度和结果。点击「取消补全」或「取消识别」停止后续识别，已导入的游戏和已补全的资料会保留。
- 点击「待核对」，对照本地名称、路径、候选封面、发售日期、开发商和匹配理由，再确认关联。也可「暂时跳过」或重新搜索。
- 没有合适候选时，仍可从游戏的「管理 → 关联作品」手动搜索。跳过只移除当前核对项；下次补全仍会检查缺少资料的游戏。

自动补全保留个人评分、收藏、分类、标签、笔记、游玩记录和已自定义的名称。目录名作为默认名称时，可更新为作品标题；本地名称中明确的版本标识（如 REMASTERED、QHD、REFLECTION BLUE）会保留。同一作品的安装合并时，会合并分类、标签、笔记和游玩记录。后台进度更新也不会重置尚未保存的编辑表单。

识别会交叉核对本地名称、编号、完整作品详情及必要的发行版本资料。旧 PotatoVN 资料中的编号可能来自先前的错误关联，必须有独立的本地线索支持。只有名称相近、证据冲突或候选难分的结果会留在核对队列；请特别留意本篇、续作、FD 和不同版本。

也可以在「发现作品」搜索并加入书架，作为尚未安装的愿望清单。

### 3. 启动与计时

点击「启动」后记录本次游玩时长，按秒累计并定期保存检查点。常见的启动器退出后，会尝试接续跟踪同一游戏目录内新出现的游戏进程。

- 计时期间关闭主窗口，会缩到托盘；双击托盘图标可重新打开。
- 点击「结束计时」只停止记录，不会关闭游戏。
- 从托盘菜单「退出管理器」退出时，会保存本次记录。
- 「高级启动参数」使用 JSON 字符串数组，例如 `["-windowed"]`；每个数组元素是一项参数。

计时反映被跟踪进程的运行时长，包括游戏在后台运行的时间。程序异常终止时，最近一次检查点之后的时间可能尚未保存。

### 4. 整理书架

在「管理」页修改名称、游玩状态、0–10 分个人评分、分类、个人标签和笔记。书架支持多字段搜索、快捷视图，以及状态、收藏、分类、标签、个人评分的组合筛选。0 分也属于已评分。

点击「选择整理」，勾选当前结果中的作品，填写需要调整的状态、收藏、分类或标签，再点击「应用」。分类和标签按逗号或换行分隔，支持添加或移除；已有内容不会因添加被整组覆盖。改变搜索或筛选后，不可见作品会取消勾选；按 Escape 退出整理。列表和封面视图、排序、概览显示状态在本机自动保存。

概览的「继续游玩」按在玩状态和最近记录推荐作品；正在计时期间可查看当前作品。统计中的日期按本地时区计算，跨日时长按记录起止区间分摊；原记录没有保存暂停发生的位置，因此跨日分布为估算。只有累计总数而没有日期的历史时长会单独注明。

作品详情展示简介、封面、开发商、角色与声优、标签和来源链接。来源评分保留各站原始尺度，个人评分单独保存；未知评分尺度暂不展示。

## 本地数据与备份

默认数据目录继续使用 `%APPDATA%\KunGalManager`，与旧版鲸屿共用同一书架，也可以从「偏好设置 → 数据文件夹」打开。

- `library.json`：书架、作品资料、本地安装路径、笔记和游玩记录。
- `library.json.bak`：上一次有效书架；主文件损坏时会尝试恢复，并保留损坏文件。
- `settings.json`：界面与 API 设置，其中密钥为加密内容。
- `metadata-matching.json`：最近的补全进度与待核对队列。重启后保留队列；中断的任务标记为已停止，可重新点击「补全资料」。

「导出书架」生成JSON备份；「导入备份」添加尚未存在的条目，重复游戏、作品或目录会跳过。备份包含本地封面压缩副本与每游戏展示选择，不包含游戏本体、存档、密钥或全局设置；远程封面只保留网址。换机后需要确认原有安装路径仍然有效。

已保存的文字资料、分类、笔记、游玩记录和本地封面副本可离线查看，本地游戏也可离线启动。搜索、刷新资料、首次加载或改选远程图片需要联网；远程图片没有独立的离线缓存。

从书架移除条目只删除管理记录，保留磁盘中的游戏文件。

API 请求在 Electron 主进程中发出，逐次添加 Bearer 鉴权，禁止自动重定向。默认一次操作的总超时为 45 秒；临时服务错误最多重试两次，限流等待尊重 `Retry-After`，配额耗尽不重试。作品被合并时会有限次跟随新 ID，并检查循环。

作品搜索使用 `catalog/search?object=work&q=...`，搜索后通过 `catalog/works?ids=...` 批量读取封面资料，保留搜索结果的顺序与分页；已失效或不可见的作品会跳过。详情使用 `catalog/works/{id}`。这是返回 JSON 的作品目录接口，没有 LLM 模型参数或 SSE 文本生成。分块传输的 JSON 会完整读取后解析。接口参考：[NextMoe 原生应用文档](https://developer.nextmoe.dev/docs/native-app)。

### 自动识别如何使用本地线索

| 线索 | 读取与使用方式 |
| --- | --- |
| 程序版本资源（默认开启，可关闭） | 仅在开启「读取程序内的游戏名称」后，在选定游戏目录内按数量、大小和资源边界限制读取 PE 的 `ProductName`、`FileDescription` 等字段。不会执行程序，但读取可能触发 Windows 扫描和隔离。通用引擎名、安装器和辅助工具会过滤。 |
| Steam 编号 | 读取根目录及 `steam_settings` 中已知名称的 App ID 文件和少量配置，提取独立的本地编号；与按名称推导的索引编号区分，并核对标题及版本。其他配置内容不用于查询。 |
| README 标题 | 只读取少量已知命名的文本说明，支持 UTF-8 与 GB18030；在开头有限区域中找本地索引已有的规范标题。任意说明正文不会上传为搜索内容。 |
| 手册和配置标题 | 仅读取当前选中安装内已知名称的 HTML / 文本手册，以及 `StartData/Start.ini` 等小型配置。提取标题、明确的产品名和品牌，支持 UTF-8、Shift-JIS、GB18030。每次最多读取 8 个文件；单文件超过 128 KB 则跳过，其余仅读前 32 KB。不读取父目录、不执行 HTML、不访问文档链接，也不上传完整正文。 |
| 目录、程序和资源文件名 | 保留有辨识度的名称；例如 `Rance01` 中的结构化编号不会简单当作 `Rance 1` 丢弃。资源文件只提供文件名线索。 |
| 旧资料与标题索引 | `.PotatoVN/meta.json` 的名称、编号保留为旧识别线索。本地索引按名称提供外部编号；两者都需要本地信息支持。 |

程序字段参考 [Microsoft 版本资源说明](https://learn.microsoft.com/en-us/windows/win32/menurc/versioninfo-resource)。Steam 官方说明了根目录 `steam_appid.txt` 的开发用途；应用另外兼容已知的嵌套配置位置，但这些文件中的编号仍可能过时或被替换，需要交叉核对。[Steamworks App ID 文档](https://partner.steamgames.com/doc/sdk/api)

标题和编号分别记录来源。由同一名称衍生的别名、索引编号，以及重复的程序和资源文件名，不会被当成多份独立证据。跨语言对应保留“实际读到的名称、同一索引行中的名称与编号”，再与候选的正式名称核对；不会把不同索引行或旧资料中的名称拼接成证明。旧资料自身的标题和编号也不能互相证明其正确性。

### 候选资料与自动关联条件

应用将 VNDB、Bangumi、Steam 编号通过 NextMoe 的 `catalog/works?refs=...` 分批查询；必要时再搜索名称。集合接口的 `include=titles` 只提供选定的罗马字和本地化名称，完整 `titles[]` 位于作品详情。识别器因此最多补读三个候选的完整详情，优先检查有独立编号支持的候选，再重新排序，并复用已读取的详情。需要辨别版本时，会受限读取 `catalog/works/{id}/releases`，核对有编号支持的作品下是否存在对应的正式发行名称。接口约定见 [NextMoe 字段裁剪与批量读](https://developer.nextmoe.dev/docs/shaping) 和[官方 OpenAPI](https://api.nextmoe.dev/v2/catalog/openapi.json)。

作品标题保留官方名称、别名、缩写、罗马字、语言及机器翻译标记。候选需要满足明确的本地证据条件；单独的旧编号、缩写或罗马字不足以证明对应关系。直接读取的 Steam App ID 与名称推导的索引编号分别评估；两个实际本地编号冲突时仍需核对。明确的章节、版本或独立编号冲突会阻止自动关联，补丁和备份目录也会留待核对实际游戏根目录。

识别先区分独立本地编号、同一索引记录或正式发行验证，以及一般标题线索的证据等级。同等级有竞争力的候选之间，自动关联要求排序系数至少相差 `0.075`，并通过同名和编号冲突检查。这个系数用于排序，不是经过校准的正确概率。高分本身不能替代证据；证据接近的结果继续交给用户核对。

上游可能用多个条目表达同一作品或发行版本。只有对应证据足够时，应用才选择一个条目作为本地书架的代表资料；这不会修改、合并或删除上游条目，也不代表上游已确认合并。无法排除真实冲突时，仍保留待核对。

### 本版识别审计

- 程序名称和文件描述可能来自同一份资源，厂商也可能属于引擎；重复字段和元数据指纹不增加独立证据数量。
- PE 的完整正式标题需要相应的目录支持，或有效的独立编号／同一索引行证明。未验证的别名加厂商信息不能自动关联；厂商名称不会按任意子串认定相同。
- 已明确选择的启动程序优先提供作品线索。通用引擎、补丁安装器、卸载器等辅助程序不参与自动判定；文件资源损坏或读取期间发生变化时，跳过该份证据。
- 读取 PE 版本资源不能证明程序安全，也不能鉴定被完整复制或篡改的版本字段。真实游戏内容、合集组成和上游未收录版本仍有识别边界。

### 本地标题索引

随应用提供的 `data/title-index.json.gz` 由 [PotatoDBMapper](https://github.com/GoldenPotato137/PotatoDBMapper) 的数据库快照转换而来，包含 **56,064 条作品记录、97,038 个标题**。该派生索引保留标题和来源编号，不包含封面或简介；完整资料仍由 NextMoe 提供。

开发者可用以下命令从自己的公开上游快照重建索引：

```powershell
python scripts/build-title-index.py path/to/vn_mapper.db
```

转换脚本只读源数据库，保留 VNDB 编号，并仅收录上游匹配相似度至少为 0.95 的 Bangumi、Steam 映射。输出记录源快照的 SHA-256，生成确定性的压缩文件；运行桌面应用不需要 Python 或 SQLite。数据来源及 Apache-2.0 许可证见 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) 和 [data/LICENSE-PotatoDBMapper.txt](data/LICENSE-PotatoDBMapper.txt)。

## 当前边界

当前暂未提供云同步、Steam 库自动扫描、`.bat` / `.lnk` 启动、自动补丁安装、压缩包自动解包、仅统计前台时间，以及 PotatoVN 全量数据迁移。读取游戏目录中的 PotatoVN 资料文件只用于识别名称和作品编号。

标题索引是随版本发布的快照，没有自动更新功能。合集、缩写、改名目录、版本差异和未收录作品可能需要人工核对；上游缺少封面时，补全也无法生成封面。「补全资料」会跳过完整条目；「重新识别」可重新读取这些条目的本地线索，需要更新现有关联资料时也可在详情中刷新。一次只运行一个识别任务，退出应用会停止未完成的任务。

NextMoe 的一个作品条目可能聚合多个发行版本，也可能存在标题接近的独立条目。发行版本校验能补充对应关系，但不会检查安装包的实际内容；绑定资料不能证明本地文件完整或一定属于该版。本地版本名称会保留，发行资料缺失或存在真实冲突时仍需核对。程序版本字段也可能只有引擎名称，或沿用旧版内容。

开启程序内名称读取后，识别器产生的程序元信息摘要只覆盖有限的版本资源和程序名，并非完整文件的身份标识。它不会用于自动绑定作品，也不能证明两个安装的游戏内容相同。保持该选项关闭时，部分缺少标题线索的条目可能需要手动关联。

复杂的外部启动器、转区工具或运行在游戏目录之外的子进程可能需要另行配置；当前接续跟踪限于同一游戏目录。界面仅支持同时跟踪一个游戏。
